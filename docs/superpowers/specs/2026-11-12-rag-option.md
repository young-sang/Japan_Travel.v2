# RAG 도입안 (검토)

- 날짜: 2026-11-12
- 관련: [회원별 여행지 추천 설계](2026-11-12-recommend-api-design.md) §10 (기각한 대안)
- 왜 이 문서가 있나: 추천 기능에 RAG 를 "쓰지 않는다"로 넘기기 전에, **쓴다면 실제로 무엇을 만들게 되는지**와 그때 무엇이 좋아지고 나빠지는지를 숫자로 남긴다. 보고서의 "검토했지만 기각한 대안"은 이 문서를 가리킨다.

## 1. 먼저, 측정값 하나가 판단을 거의 다 한다

| 항목 | 실측 (2026-11-12, `data.sql`) |
|---|---|
| 여행지 | 219곳 |
| 설명 길이 | 최소 22자 · **중앙 37자** · 최대 57자 |
| 219곳 전부의 이름 + 현 + 설명 | **10,572자 ≈ 약 1만 토큰** |

**여행지 전체가 한 번의 프롬프트에 들어간다.** `gpt-5-mini` 입력 단가로 호출당 약 $0.0025(3 ~ 4원)다.

RAG 가 존재하는 이유는 "다 넣을 수 없으니 질문과 관련된 조각만 찾아 넣는다"다. 그 전제가 이 데이터에는 없다. 그래서 **"검색해서 문서를 물려주는" 형태의 RAG 는 이 프로젝트에서 아무것도 더하지 못한다** — top-k 를 219로 잡은 것과 결과가 같아진다.

다만 "RAG" 를 조금 넓게 보면, **임베딩 유사도를 쓰는 것**은 얘기가 다르다. 아래로 갈래를 나눈다.

## 2. 세 갈래

| 갈래 | 무엇 | 이 프로젝트에서 |
|---|---|---|
| **A. 생성 보강형 RAG** | 질의로 문서 top-k 검색 → 프롬프트에 넣어 LLM 이 답 | **억지.** 전체가 1만 토큰이라 검색 단계가 하는 일이 없다 |
| **B. 임베딩으로 후보 선정** | 찜한 곳들의 설명 벡터 평균 = 취향 벡터, 코사인 상위 40곳을 후보로 | **억지 아님.** 지금 설계의 약점을 정확히 메운다 (아래 §3) |
| **C. 의미 검색** | "조용한 온천이 있는 시골" 같은 자연어로 여행지 찾기 | **가장 값있다.** 다만 전시 1주 안에는 범위가 크다 (아래 §6) |

사용자가 "억지 같다"고 한 직관은 **갈래 A 에 대해 맞다.** 넣는다면 B 다.

## 3. 갈래 B 가 메우는 약점

지금 기획서(§4)의 후보 선정은 **"찜한 곳의 현"** 으로 좁힌다. 여기에 두 구멍이 있다.

- `destinations` 에 **테마 태그 컬럼이 없다**(S7 백로그). 그래서 "사찰을 좋아한다"는 성향을 후보 단계에서 전혀 쓰지 못하고, LLM 이 프롬프트에서 설명을 읽을 때 처음 반영된다.
- 같은 현 안에서만 찾으니 **"교토의 사찰을 좋아하는 사람에게 나라의 사찰"** 같은 추천이 후보에 아예 안 들어온다. 현을 넘는 취향 연결이 끊긴다.

갈래 B 는 설명 문장을 벡터로 바꿔 두므로, 태그 컬럼 없이 "비슷한 설명을 가진 곳"을 현과 무관하게 찾는다. 이건 SQL 로 못 하고 LLM 프롬프트로도 (219곳을 다 넣지 않는 한) 못 한다.

**그리고 런타임에 API 호출이 0이다.** 색인을 미리 만들어 레포에 넣어 두면, 질의 벡터는 "찜한 곳들의 **저장된** 벡터 평균"이라 새로 임베딩할 것이 없다. 즉 **키가 없어도 갈래 B 는 돈다.** 기획서 §6 의 폴백이 "인기 상위"에서 "취향 기반 유사도"로 올라간다 — 폴백 품질이 오히려 좋아지는 구조다.

## 4. 갈래 B 를 넣으면 만들게 되는 것

### 4-1. 임베딩 모델

OpenAI `text-embedding-3-small`. `dimensions` 를 **256 으로 줄여서** 받는다(기본 1536).

| | 1536차원 | 256차원 |
|---|---|---|
| 색인 파일 크기 | 약 1.3 MB (float32) | **약 224 KB** |
| 219곳 코사인 1회 | 수십 µs | 수 µs |
| 219건 규모에서 품질 차이 | 사실상 없음 | |

**색인 비용** — 219건 × 약 70토큰 = 약 15,000 토큰, `$0.02 / 1M` 단가로 **$0.0003**. 백 번 다시 만들어도 40원이다. 비용은 논점이 아니다.

### 4-2. 벡터 저장소 — 3안

| 안 | 내용 | 평가 |
|---|---|---|
| **① 파일 색인 + 자바 완전탐색** | `embeddings.json`(224 KB)을 리소스로 커밋, 기동 때 메모리에 올리고 219건 코사인을 돌린다 | **추천.** 새 의존성 0, 스키마 변경 0, 배포 변화 0. 219건에 인덱스 자료구조가 필요 없다 |
| ② MySQL 테이블에 BLOB | `destination_embeddings` 테이블 추가 | 전시 1주 전 스키마 변경. 파일로 충분한데 되돌릴 것이 늘어난다 |
| ③ 별도 벡터DB (Qdrant · Chroma · pgvector) | 컨테이너를 하나 더 띄운다 | **기각.** EC2 에 compose 로 MySQL · 백엔드 · nginx 가 이미 떠 있다(D-085 · D-086). 219건에 과하고 배포가 더 복잡해진다 |

### 4-3. Spring AI 를 쓸지

`spring-ai-openai` 의 `VectorStore` · `SimpleVectorStore` 가 ① 안에 대응한다. 다만 두 가지가 걸린다.

- **Boot 버전** — 이 프로젝트는 Spring Boot 3.3 이다. Spring AI 1.0 계열은 더 높은 Boot 를 요구할 수 있어 **확인이 필요하다.** 전시 1주 전에 Boot 를 올리는 건 하지 않는다.
- 219건 코사인은 직접 쓰면 50줄이 안 된다. 추상화를 들이는 이득이 적다.

→ **직접 구현을 추천한다.** 임베딩 호출은 색인 스크립트(파이썬)에서 하고, 자바는 파일을 읽어 코사인만 돈다. 즉 **백엔드에 새 의존성이 하나도 안 붙는다.**

### 4-4. 청킹

**필요 없다.** 설명이 최대 57자라 한 곳 = 한 청크다. 청킹 전략, 겹침 크기, 문서 분할은 논의할 거리가 없다 — 이것도 이 데이터에 RAG 가 과하다는 신호다.

### 4-5. 조각 목록

| # | 조각 | Red (TDD) | 인수 기준 |
|---|---|---|---|
| R1 | 색인 생성 스크립트 | — (스크립트) | `scripts/build_embeddings.py` 가 219건을 임베딩해 `backend/src/main/resources/embeddings.json` 을 만든다. **캐시를 두어 다시 돌려도 같은 파일이 나온다**(`fetch_commons_images.py` 와 같은 방식, S3e 에서 이 성질이 도움이 됐다). 파일은 레포에 커밋한다 |
| R2 | 유사도 후보 선정 | 통합 테스트 — 찜 목록이 같으면 후보 40곳이 **결정적으로** 같다. 찜한 곳 · 본 곳은 후보에서 빠진다. 색인 파일이 없으면 기존 규칙 후보로 떨어진다 | 기획서 §4 의 규칙 후보와 교체 가능하다. 키 없이 동작한다 |

**시간: 반나절.** 조각 1 ~ 3(규칙 → 화면 → OpenAI)이 끝난 뒤 얹는 선택 조각이고, 빼도 기능은 완결이다.

## 6. 갈래 C (의미 검색) — 값은 가장 크지만 지금은 아니다

`GET /api/search/semantic?q=` 를 만들고 질의를 임베딩해 코사인 상위를 돌려주면, 지금 백로그의 세 가지가 한꺼번에 풀린다.

- **S7 테마 태그** — 태그 컬럼 없이 "온천" · "자연" · "사찰"로 찾아진다. 테마 태그 스프린트 자체가 필요 없어질 수 있다
- **S8 검색 보완 · C-10** — 오타 검색이 0건으로 끝나던 문제가 의미 유사도로 풀린다
- 발표에서 "태그 없이 뜻으로 찾는다"는 이야기가 된다

다만 질의 임베딩에 키가 필요해져 **키 없으면 검색이 죽는다**(기존 이름 검색으로 폴백은 가능). 그리고 검색 화면 · 결과 정렬 · 폴백 분기까지 하면 반나절을 넘긴다. **전시 후 S8 에서 하는 쪽을 추천한다.** 지금 하면 S9 결과물이 밀린다.

## 7. 판단

- **갈래 A 는 기각을 유지한다.** 전체가 1만 토큰이라 검색 단계가 하는 일이 없다.
- **갈래 B 는 선택 조각(R1 · R2)으로 둔다.** 조각 1 ~ 3 이 끝나고 S9 결과물까지 손에 들어온 뒤, 예비일(6 ~ 7일차)에 시간이 남으면 얹는다. 빼도 추천 기능은 완결이고, 얹으면 후보 품질과 폴백 품질이 같이 올라간다.
- **갈래 C 는 전시 후 S8 로 넘긴다.**

RAG 를 "넣는다/안 넣는다"가 아니라 **"검색 단계를 벡터 유사도로 할지, 이력 기반 SQL 로 할지"** 가 실제 선택지다. 지금 설계는 후자이고, 그건 RAG 를 몰라서가 아니라 데이터가 219건이기 때문이다.

## 8. 보고서에 쓸 문단 (그대로 쓸 수 있게)

> 추천 기능에 RAG(검색 보강 생성)를 적용할지 검토했다. 측정 결과 여행지 219곳의 이름 · 지역 · 설명을 모두 합쳐도 약 1만 토큰이어서 전체가 한 번의 프롬프트에 들어갔다. RAG 는 문맥에 다 담을 수 없는 문서에서 관련 조각을 골라내기 위한 구조이므로, 전체가 들어가는 규모에서는 검색 단계가 결과를 바꾸지 못한다고 판단해 도입하지 않았다. 대신 사용자의 찜 · 열람 · 평점 이력으로 후보를 좁히는 SQL 단계를 두어, 검색에 해당하는 역할을 데이터 규모에 맞는 방식으로 대체했다. 한편 임베딩 유사도를 후보 선정에 쓰는 방식은 지역이 아닌 설명 의미로 취향을 연결할 수 있어 별도 선택 과제로 남겼고, 자연어 의미 검색은 테마 태그 부재와 오타 검색 문제를 함께 해결할 수 있어 다음 과제로 정리했다.
