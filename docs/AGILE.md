# 하이퍼 애자일 진행 규칙

졸업작품 보완 작업(2026-11-04~)을 이 규칙으로 진행한다. 정한 경위는 [D-071](DECISIONS.md#d-071--보완-작업은-하이퍼-애자일-규칙docsagilemd-으로-진행한다).

핵심은 하나다. **스프린트가 하나 끝날 때마다 시연할 수 있는 상태를 유지한다.** 그러면 언제 멈춰도 그 시점의 결과물로 발표할 수 있다.

## 1. 리듬

| 항목 | 규칙 |
|---|---|
| 스프린트 길이 | 반나절에서 하루. 넘칠 것 같으면 범위를 자른다. 기간은 늘리지 않는다 |
| 동시 진행 | 한 번에 스프린트 하나만 진행한다 (WIP 1) |
| 릴리스 | 스프린트 몇 개를 묶은 단위. 끝나면 git 태그(`release-N`)를 찍고 push 여부를 묻는다 |
| 순서 | 아래 백로그의 우선순위를 따른다. 바꾸는 건 스프린트 사이에만 한다 |

## 2. 스프린트 한 바퀴

### ① 시작

1. 백로그 항목을 이번 스프린트의 할 일 목록(task list)으로 쪼갠다.
2. 이번에 **하지 않을 것**을 한 줄 적는다.
3. 시작하기 전에 보이는 갈림길이 있으면 결정 게이트(③)를 먼저 연다.

### ② 진행

- 할 일 목록을 실시간으로 갱신한다.
- DB를 지우거나 바꾸기 전에는 반드시 백업한다. 백업 위치는 `data/*.bak_*`이다(CLAUDE.md DB 규칙).
- 범위 밖의 일이 보이면 손대지 않고 백로그에 적어 둔다. 단, 이번 스프린트의 결과물을 망가뜨리는 버그라면 고친다.

### ③ 결정 게이트: 매번 묻는다

갈림길이 나오면 **크기와 상관없이 멈추고 사용자에게 묻는다.**

- 선택지는 2~4개로 제시한다. 추천안을 맨 앞에 두고 `(Recommended)`를 붙인다.
- 선택지마다 무엇이 달라지는지 한 줄로 적는다.
- 답을 받으면 그 자리에서 `docs/DECISIONS.md`에 기록한다. 고르지 않은 안은 "기각"에 이유와 함께 적는다.
- 변수명이나 파일 위치처럼 되돌리기 쉬운 것은 갈림길로 치지 않는다. DECISIONS의 "기록하지 않을 것" 기준을 따른다.

### ④ 완료 기준 (Definition of Done)

아래를 모두 만족해야 스프린트가 끝난다.

- [ ] 바뀐 화면을 브라우저(:5173)에서 직접 확인했다. 시연 계정 `demo`로 확인할 수 있는 건 로그인해서 본다
- [ ] 백엔드 테스트 120개 이상이 통과한다(`./gradlew test`). 테스트 수는 줄지 않는다
- [ ] 프론트 빌드(`npx vite build`)가 통과한다
- [ ] 이번에 내린 결정이 모두 DECISIONS에 있다
- [ ] 실행 방법이 바뀌었으면 README에 반영했다
- [ ] 커밋했다. push는 하지 않는다

### ⑤ 끝: 데모 · 회고 · 승인

다음 내용을 한 번에 보고한다.

1. **데모**: 무엇이 바뀌었는지 표로 정리하고, 확인한 증거(화면 캡처, 건수)를 붙인다.
2. **완료 기준 결과**: 통과하지 못했거나 확인하지 못한 항목은 그대로 밝힌다.
3. **회고 한 줄**: 다음 스프린트에 영향을 주는 사실을 적는다.
4. **백로그 변경**: 새로 생긴 항목이나 순서 조정 제안이 있으면 적는다.
5. 아래 스프린트 로그에 한 줄을 추가한다.

그다음 **멈춘다.** 사용자가 "S다음 시작"이라고 하기 전에는 다음 스프린트에 들어가지 않는다.

## 3. 커밋 · push

- 스프린트마다 커밋한다. 커밋이 여러 개여도 된다. 메시지 끝에는 관련 D 번호를 붙인다.
- 내가 만들지 않은 파일(`.agents/`, `.codex/`, `AGENTS.md` 등)은 커밋하지 않는다.
- push와 태그 push는 매번 묻는다.
