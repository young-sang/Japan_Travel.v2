# 의사결정 기록

이 프로젝트에서 **왜 그렇게 하기로 했는지**를 모아둔다. 무엇을 만들었는지는 코드와
설계 문서가 말해주지만, 왜 다른 길을 안 갔는지는 어디에도 남지 않는다. 그걸 남긴다.

## 쓰는 법

- 결정이 내려질 때마다 **맨 아래에 추가**한다. 번호는 이어서 붙이고 줄이지 않는다.
- 결정이 **뒤집히면 지우지 않는다.** 원래 항목의 상태를 `번복됨`으로 바꾸고 새 번호를
  가리킨다. 번복 자체가 기록할 값어치가 있다.
- **기각한 대안을 반드시 쓴다.** 나중에 같은 고민이 돌아왔을 때 이미 검토했다는 걸
  아는 것이 이 문서의 절반이다.
- 한 항목은 짧게. 길어지면 `docs/superpowers/specs/` 에 문서를 만들고 여기서 링크한다.

| 상태 | 뜻 |
|---|---|
| `확정` | 지금 유효하다 |
| `보류` | 결정을 미뤘다. 언제 정할지 적어둔다 |
| `번복됨` | 더 이상 유효하지 않다. 대체 항목 번호를 적는다 |

### D-001 · 리팩토링이 아니라 도메인별 신규 작성

**2026-09-15 · 확정**

옛 코드를 옮기는 대신 `_repo/` 아래에 도메인별로 새로 짓기로 했다.

**이유** — 1순위 목표가 구조 개선이 아니라 **코드 이해**다. 남의 코드를 옮기면
옮기는 법만 배우고, 새로 지으면 왜 그 구조인지를 배운다.

**기각** — 기존 코드를 계층별로 이동시키는 리팩토링 계획 (문서 2건 폐기).

### D-002 · Maven → Gradle, JdbcTemplate → JPA

**2026-09-15 · 확정** · 커밋 `7b56062`

**이유** — JPA 를 쓰기로 했고, Spring Boot 3.3.4 는 Gradle 9 를 지원하지 않아
Gradle 8.14.5 (Groovy DSL) 로 고정했다.

**영향** — `ddl-auto: none` · `open-in-view: false`. 스키마의 주인은 `schema.sql` 이고
Hibernate 는 스키마를 건드리지 않는다. SQLite 는 공식 dialect 가 없어
`hibernate-community-dialects` 를 쓴다 — 예상 밖 동작이 나오면 **그 지점만**
`nativeQuery = true` 로 우회한다.

### D-004 · API 계약과 스키마를 고정한다

**2026-09-15 · 번복됨 → [D-008](#d-008--프론트를-백엔드에-맞춘다-전제-3개-해제)**

### D-005 · 예외 → 상태코드 번역기를 한 곳에 둔다

**2026-09-17 · 확정**

Service 가 `NotFoundException` · `ForbiddenException` · `ConflictException` 을 던지고,
`ApiExceptionHandler` 하나가 404 · 403 · 409 로 번역한다.

**이유** — 컨트롤러에서 `if (empty) return notFound()` 를 하면 같은 판단이 일반
컨트롤러와 관리자 컨트롤러 양쪽에 생긴다. 규칙이 두 군데로 갈라진다.

**세부** — `ConflictException` 은 선택적 `code` 와 `extra` 를 들고 다니며 `body()` 로
응답 맵을 **스스로** 조립한다. 핸들러가 조립하면 거기에 `if (code != null)` 이 생기기
때문이다. **핸들러에 `if` 나 `instanceof` 가 들어가면 설계가 깨진 것이다.**

**금지** — `@ExceptionHandler(Exception.class)` catch-all. `ResponseStatusException` 을
가로채 상태코드를 바꿔버린다.

### D-008 · 프론트를 백엔드에 맞춘다 (전제 3개 해제)

**2026-09-17 · 확정** · [D-004](#d-004--api-계약과-스키마를-고정한다) 를 대체

프론트엔드 · API 계약 · DB 스키마가 모두 자유로워졌다. 기존 앱은 **기능 명세서**
역할만 한다. 프론트는 백엔드가 굳은 뒤 마지막 Task 에서 맞춘다.

**전제가 된 사실** — 현재 DB 내용은 테스트용 더미다. 옮길 실데이터가 없으면
스키마를 갈아엎는 비용이 거의 0이다. 따라서 **지금 완벽한 설계를 할 필요가 없고,
만들다가 잘못을 발견하면 바꾼다.**

**대가** — 회귀 안전망이던 `baseline/` diff 가 무효가 됐다 ([D-016](#d-016--baseline-diff-를-스모크-스크립트로-대체한다)).

**영향** — 설계 문서 2건 폐기, [2026-09-17-greenfield-rebuild-design.md](superpowers/specs/2026-09-17-greenfield-rebuild-design.md) 로 대체.

### D-009 · 1차 범위에서 관리자·수집기·감사로그·모니터링을 뺀다

**2026-09-17 · 확정**

도메인 14 → 10, 엔드포인트 약 55 → 30.

**뺀 것** — 관리자 화면·API 전부 / Wikipedia 수집기 (858줄) / 수집 모니터링
(`bulk_runs` · `collector_runs` · `ZombieWatcher` · `BulkProgress` 360줄 ·
`CollectionStatus` 470줄) / 감사 로그 / 캐시 창구 / 대시보드 통계 /
`collections` · `collection_items` · `achievements` (0행, 자바 코드가 참조하지 않음).

**이유** — 모니터링은 프로젝트 `CLAUDE.md` 의 기본 제외 항목이다. 감사 로그는 10개
도메인 전부의 Service 에 한 줄씩 들어가 결합을 만든다. 관리자 기능은 나중에 필요한
것만 추려서 다시 만든다 — **영구 폐기가 아니라 범위 축소다.**

**남긴 것** — `users.role` 컬럼. 나중에 필요하고 컬럼 하나는 비용이 아니다.
1차에서는 권한 분기를 쓰지 않는다.

**주의** — 수집기를 빼면 `places` 를 채울 방법이 시드뿐이다 ([D-015](#d-015--옛-db-에서-변환해-시드한다)).

### D-010 · destinations + festivals → places 한 테이블

**2026-09-17 · 번복됨 → [D-022](#d-022--places-를-destinations-와-festivals-로-다시-나눈다)**

`kind` 컬럼(`'destination'` | `'festival'`)으로 구분한다.

**이유** — 두 테이블의 컬럼이 거의 같았다. `name` · `prefecture` · `lat` · `lng` ·
`image_path` · `description` · `wiki_title` · `last_refreshed_at` 이 동일하고 축제에만
`month` · `date_text` 가 더 있었다. 사실상 같은 테이블이었다.

**대가** — `month` · `date_text` 에 `NOT NULL` 을 걸 수 없다. 관광지 행에서는 NULL 이다.
반대 방향은 `CHECK (kind <> 'destination' OR (month IS NULL AND date_text IS NULL))`
로 막는다.

### D-011 · 활동 대상을 places 로 한정해 다형성을 없앤다

**2026-09-17 · 확정**

즐겨찾기 · 리뷰 · 방문기록은 `places` 만 가리킨다. 코스는 대상이 아니다.

**문제** — 옛 스키마는 `target_type` + `target_id` 로 "관광지·축제·코스 중 아무거나"를
가리켰다. FK 컬럼 하나는 테이블 하나만 가리킬 수 있으므로 FK 를 걸 수 없었고,
그래서 관광지를 지울 때 자바가 손으로 `favorites` · `reviews` · `history` 를 지우고
있었다 — **DB 가 할 일을 자바가 대신했다.**

**검토하고 기각한 대안**

| 안 | 내용 | 기각 이유 |
|---|---|---|
| A 레지스트리 | `content` 상위 테이블 + JOINED 상속 | DB 자체가 처음인데 **이해 안 되는 구조 위에 10개 도메인을 쌓게 된다.** 목표(코드 이해)와 정반대 |
| B nullable FK | `favorites(place_id, course_id)` + CHECK | 컬럼 중 하나는 항상 NULL. 대상이 늘면 세 테이블에 컬럼 추가 |
| C 테이블 분리 | `favorites` + `course_favorites` … | 테이블 6~9개, 합친 목록 조회가 UNION |
| D 단일 테이블 | 셋을 한 테이블에 | `NOT NULL` 제약을 거의 못 검 |
| E 트리거 | 지금 모양 + DELETE 트리거 | 로직이 자바 코드에 안 보인다 |

**왜 한정으로 풀었나** — 대상이 하나면 문제 자체가 사라진다. 평범한 FK 하나씩이고
CHECK 도 NULL 컬럼도 새 개념도 없다. 코스 즐겨찾기가 필요해지면 `course_favorites`
테이블을 **추가만** 하면 된다 — 기존 테이블을 한 줄도 건드리지 않는다.

> 근거로 쓰지 않은 것: "코스 활동 0건". 데이터가 더미이므로 사용량은 증거가 아니다.
> 이것은 **범위 축소 결정**이지 사용량 판단이 아니다.

### D-012 · 태그와 타임라인을 행으로 정규화한다

**2026-09-17 · 확정**

`tags TEXT` → `place_tags` · `course_tags`. `timeline_json TEXT` → `course_stops`.

**이유(태그)** — 검색이 `LIKE '%"온천"%'` 이었다. 행으로 빼면 `WHERE tag = '온천'` 이
되고 인덱스가 먹는다. JPA 쪽에서도 `AttributeConverter` 가 필요 없어진다.

**이유(타임라인)** — 옛 `timeline_json` 은 `title` · `desc` · `lat` · `lng` 를 복사해
두어 코스와 장소 사이에 링크가 없었다. 확인해 보니 `CourseBuilder.jsx` 는 정류장을
만들 때 항상 실제 장소에서 가져오고 `targetId` 를 이미 들고 있다. 따라서
`place_id NOT NULL` 참조만 하면 되고 표시용 값은 조인으로 얻는다.

**검토하고 기각** — 참조 + 스냅샷 컬럼 병행 (원본 삭제에 대비). 정류장이 항상 실제
장소에서 오는 것이 확인되어 불필요했다.

### D-021 · 데이터를 생성형 AI 로 만든다

**2026-09-18 · 확정** · [D-015](#d-015--옛-db-에서-변환해-시드한다) 를 대체

관광지·축제 데이터를 Wikipedia 수집 대신 **생성형 AI 로 만들어 시드**한다.
옛 db 의 118·26건은 쓰지 않는다.

**이유** — 수집기를 1차 범위에서 뺐고([D-009](#d-009--1차-범위에서-관리자수집기감사로그모니터링을-뺀다)),
옛 db 데이터도 결국 Wikipedia 에서 온 것이라 같은 경로다. 새 스키마에 맞춰
처음부터 만드는 편이 깨끗하고 변환 스크립트도 필요 없다.

**스키마에 미치는 영향**
- `wiki_title` 제거 — UPSERT 키로 쓰던 주체(수집기)가 없다.
- `last_refreshed_at` 제거 — 갱신하는 주체가 없다.
- **중복 방지 수단이 바뀐다.** `UNIQUE(wiki_title)` 대신
  `UNIQUE(name, prefecture)` 로 같은 지역의 동명 장소를 막는다. 표기 차이
  (`후시미이나리 신사` vs `후시미 이나리 타이샤`)까지는 못 막지만 없는 것보다 낫다.

**남은 문제 (Task 7 에서 정한다)**
- **이미지 출처.** 옛 데이터는 Wikipedia 이미지 경로를 썼다. AI 는 이미지를 만들지
  못하므로 `image_path` 를 무엇으로 채울지 정해야 한다. 당장은 NULL 허용으로 두고
  프론트에서 플레이스홀더를 쓰거나, 정적 이미지를 넣는다.
- **좌표 정확도.** AI 가 만든 `lat`/`lng` 는 틀릴 수 있다. 지도에 엉뚱한 핀이 꽂히면
  좌표만 따로 손보거나 NULL 로 두는 편이 낫다.

**나중에 수집기가 돌아온다면** — `wiki_title` 컬럼을 그때 추가한다. 컬럼 추가는
기존 데이터를 건드리지 않는 변경이라 지금 미리 둘 이유가 없다
([D-020](#d-020--스키마를-도메인별로-늘려간다) 과 같은 태도).

### D-022 · places 를 destinations 와 festivals 로 다시 나눈다

**2026-09-18 · 확정** · [D-010](#d-010--destinations--festivals--places-한-테이블) 을 대체

관광지와 축제를 각각의 테이블로 둔다.

**이유** — 테이블 하나에 한 종류를 담는 것이 **DB 를 처음 배울 때 익숙한 방식**이다.
[D-011](#d-011--활동-대상을-places-로-한정해-다형성을-없앤다) 에서 레지스트리를 접은
것과 같은 판단이다: 이해되는 구조로 시작하고, 필요해지면 그때 바꾼다.

**얻는 것**
- `festivals.month` 에 `NOT NULL` 을 걸 수 있다. D-010 이 "대가" 로 적어둔 그것이다.
- `kind` 컬럼과 그에 딸린 CHECK 두 개가 사라진다. 모든 조회에 `WHERE kind = ?` 를
  붙일 필요도 없다.
- **태그 테이블이 하나로 줄어든다.** 옛 스키마의 `festivals` 에는 `tags` 가 없었다.
  합쳤을 때는 축제에도 태그가 딸려왔지만, 나누면 `destination_tags` 만 있으면 된다.
- Task 가 자연스럽게 갈라진다. Task 1 은 `destination` 만, `festival` 은 같은 패턴을
  반복하는 Task 2 가 된다. 처음 배울 때 유리하다.

**대가 — Task 3 에서 청구된다**

활동(즐겨찾기·리뷰·방문기록)이 가리킬 대상이 다시 둘이 되므로 다형성 문제가
돌아온다. **테이블 분리로 처리한다** — `favorite_destinations` ·
`favorite_festivals` · `review_destinations` … 3종 × 2대상 = **6개.**
각각은 평범한 FK 하나뿐이라 새로 배울 개념이 없다. 레지스트리로 가지 않는다.

같은 컬럼 8개(`name` · `prefecture` · `description` · `lat` · `lng` · `image_path` ·
`created_at` · `id`)를 두 테이블이 중복해서 갖는다. `/api/search` 도 두 테이블을
조회해 합쳐야 한다.

**나중에 합치고 싶어지면** — Task 3 에서 반복이 번거롭게 느껴지면 그때 합친다.
데이터가 더미이므로 비용은 여전히 낮다 ([D-020](#d-020--스키마를-도메인별로-늘려간다)).

### D-023 · 지역과 태그를 참조 테이블로 둔다

**2026-09-18 · 확정** · [D-017](#d-017--날짜-타입api-경로prefecture-제약은-task-1-에서-정한다)
의 `prefecture` 항목을 해결한다

`prefectures(name)` 와 `tags(name)` 를 만들고, 쓰는 쪽에서 FK 로 참조한다.

**이유** — 데이터를 AI 로 만들면서([D-021](#d-021--데이터를-생성형-ai-로-만든다))
어휘가 흔들릴 위험이 생겼다. `prefecture TEXT` 는 `'도쿄'` · `'동경'` 을 그대로 받고,
그 행은 지역 필터에서 **영원히 안 걸린다 — 에러도 나지 않는다.** FK 를 걸면 없는
값은 삽입 자체가 거부된다. 어휘가 제약이 된다.

부수 효과로 `frontend/src/data/prefectures.js` 의 하드코딩된 47개를 없앨 수 있다.
나중에 `GET /api/prefectures` 로 내려주면 목록의 출처가 한 곳이 된다.

**구조가 둘로 갈린다 — 관계의 개수가 결정한다**

| | 관계 | 모양 |
|---|---|---|
| 지역 | 관광지 1 : 지역 1 (1:N) | `destinations.prefecture` FK **컬럼** |
| 태그 | 관광지 1 : 태그 N (N:M) | `destination_tags` **정션 테이블** |

목적은 같아도 "둘 다 태그니까 같은 구조" 가 아니다.

**키는 이름 자체를 쓴다** (`name TEXT PRIMARY KEY`). 지역 47 · 태그 11 이 고정
어휘라 이름이 바뀔 일이 드물고, 번호를 키로 두면 태그 이름을 쓸 때마다 조인이
붙는다. 이름 변경이 필요해지면 `ON UPDATE CASCADE` 로 처리한다.

**`ON DELETE CASCADE` 를 붙이지 않는다.** 지역·태그를 지울 때 그걸 쓰던 관광지가
딸려 사라지면 안 된다. 기본값(`NO ACTION`)이면 사용 중인 값은 삭제가 거부되고,
그게 맞는 동작이다.

**어휘 데이터는 `schema.sql` 에 `INSERT OR IGNORE` 로 넣는다.** 47개·11개는 데이터가
아니라 스키마의 일부에 가깝다. `schema.sql` 이 매 기동마다 실행되므로 `OR IGNORE`
가 필요하다 — `CREATE TABLE IF NOT EXISTS` 와 같은 이유다.

**정한 것**
- `prefectures` 에 `sort_order` 를 두지 않는다. 이름순(가나다) 정렬이면 필터 격자에서
  찾기 쉽고, 지리 순서는 일본 지리를 아는 사람에게만 의미가 있다. 필요해지면 그때
  컬럼을 추가한다.
- **축제도 태그를 쓴다.** `tags` 를 공유하고 Task 2 에서 `festival_tags` 정션만
  추가한다. 옛 앱에는 축제 태그가 없었다.
- **태그 어휘를 손본다.** 옛 11개 중 `관광지`(모든 행이 관광지라 구분이 안 됨) 와
  `축제`(이제 테이블이 그 역할) 를 뺀다. 남는 9개는 `자연` · `등산` · `바다` ·
  `온천` · `역사` · `도시` · `랜드마크` · `쇼핑` · `맛집`. 축제용 태그
  (`불꽃놀이` · `전통` · `벚꽃` 등) 는 시드를 만들 때 정한다 — 콘텐츠 판단이고
  스키마상으로는 행을 넣는 문제일 뿐이다.

### D-024 · 태그를 1차 범위에서 뺀다

**2026-09-18 · 확정** · [D-023](#d-023--지역과-태그를-참조-테이블로-둔다) 의 태그 부분을 미룬다

`schema.sql` 에 넣는 결정.

### D-025 · 참조 테이블의 키를 id 로 둔다

**2026-09-18 · 확정** · [D-023](#d-023--지역과-태그를-참조-테이블로-둔다) 의 "키는 이름
자체를 쓴다" 를 뒤집는다

`prefectures(id INTEGER PK, name TEXT NOT NULL UNIQUE)` 로 두고,
`destinations.prefecture_id` 가 `prefectures(id)` 를 참조한다.

**같이 따라오는 것 — PK 를 옮기면 원래 PK 가 하던 일을 누가 대신할지 따져야 한다.**
`name` 이 PK 였을 때는 PK 가 유일성을 보장했다. PK 를 `id` 로 옮기면 그 보장이 `id`
로 따라가므로 `name TEXT NOT NULL UNIQUE` 가 **반드시** 필요하다. 없으면
`(1,'도쿄도')` 와 `(2,'도쿄도')` 가 공존하고 어휘 통제(D-023 의 목적)가 무너진다.

**왜 뒤집었나** — D-023 에서 이름을 키로 둔 근거는 "조인 하나를 아낀다" 였다. 그런데
이 프로젝트에서 조인은 비용이 아니라 배울 거리다.

- JPA 에서 `@ManyToOne` 한 줄로 매핑되는 **표준 모양**이고, 앞으로 계속 만난다
  (`posts → users`, `course_stops → destinations`). 여기서 한 번 제대로 해두면
  나머지가 반복이다.
- 모든 테이블이 `id` 를 갖는 일관성은 읽는 사람에게 값어치가 있다.
- 텍스트를 FK 로 쓰는 것은 틀리지 않지만 흔하지 않아, 나중에 코드를 보는 사람이
  한 번 멈칫하게 된다.

**대가** — 지역 이름을 쓰려면 조인이 붙는다. `SELECT * FROM destinations` 만으로는
`prefecture_id = 13` 이 어느 지역인지 알 수 없다.

**컬럼명** — `prefecture` 가 아니라 `prefecture_id`. 값이 이름이 아니라 번호라는 것이
이름에서 드러나야 한다. `destinations` 의 유니크 제약도 `UNIQUE (name, prefecture_id)`
로 따라간다.

### D-027 · Lombok 을 쓴다

**2026-09-18 · 확정**

`build.gradle` 에 `compileOnly` + `annotationProcessor` 짝으로 넣었다 (테스트 소스셋에도
같은 짝). 버전은 Spring Boot BOM 이 관리하므로 적지 않는다 — 현재 1.18.46.

**왜 `implementation` 이 아닌가** — Lombok 은 컴파일 시점에만 필요하고 런타임에는
아무 역할이 없다. `implementation` 으로 넣으면 실행 jar 에 불필요하게 포함된다.
`annotationProcessor` 를 빠뜨리면 의존성은 잡히는데 어노테이션이 아무 코드도
생성하지 않아, **원인을 짚기 어려운 "심볼을 찾을 수 없음" 으로 나타난다.** 둘은 짝이다.

**엔티티에서 주의할 것 — `@Data` 는 쓰지 않는다.** JPA 엔티티에 `@Data` 를 붙이면
`@EqualsAndHashCode` 가 모든 필드를 쓰는데, 연관 필드가 섞이면 `hashCode()` 가 LAZY
프록시를 건드려 의도치 않은 조회가 나가거나 순환 참조로 스택오버플로가 난다.
`@ToString` 도 같은 이유로 연관 필드에서 터진다. 엔티티에는 `@Getter` +
`@NoArgsConstructor` 를 기본으로 두고, 필요한 것만 골라 붙인다.

**기각한 대안 — Lombok 없이 간다.** 보일러플레이트를 직접 쓰는 쪽이 어떤 코드가
생성되는지 명확하다는 장점은 있다. 다만 엔티티가 늘어날수록 getter/생성자가 파일의
대부분을 차지해 읽기 어려워진다. 학습 목적이라 해도 여기서 배울 것은 JPA 매핑이지
getter 타이핑이 아니라고 봤다.

**대가** — IDE 에 Lombok 플러그인이 필요하고 (IntelliJ 는 기본 번들), 어노테이션 처리가
꺼져 있으면 IDE 에서만 빨간 줄이 뜬다. [D-026](#d-026--pomxml-을-지워-빌드-도구를-gradle-하나로-굳힌다)
에서 겪은 것과 같은 "Gradle 은 되는데 IDE 만 안 되는" 증상이 나올 수 있는 지점이다.

### D-026 · MySQL 로 옮기고 Lombok 을 도입한다

**2026-09-18 · 확정** · [D-002](#d-002--maven--gradle-jdbctemplate--jpa) 의 SQLite 부분과
[D-017](#d-017--날짜-타입api-경로prefecture-제약은-task-1-에서-정한다) 의 날짜 항목을 해결한다

DB 를 SQLite 에서 **MySQL 8** 로 바꾼다. 그리고 보일러플레이트를 줄이기 위해
**Lombok** 을 쓴다.

**MySQL 로 옮긴 이유** — 최종 목적지가 MySQL 이고, 코드가 5개 파일 · 데이터가 0 인
지금이 가장 싸다. "양쪽에서 다 도는 이식 가능한 DDL" 은 반쪽짜리다 —
`AUTO_INCREMENT` 하나만으로도 교집합이 깨지므로 어차피 옮길 때 다시 써야 한다.

**같이 해결되는 것**
- SQLite 는 공식 Hibernate dialect 가 없어 커뮤니티 구현을 쓰고 있었다 (D-002 의
  리스크). MySQL 은 공식 dialect 가 있다.
- 날짜를 `TEXT` 로 두고 자바 타입을 미뤄뒀는데(D-017), MySQL 에는 `DATETIME` 이
  있으므로 `LocalDateTime` 을 그냥 쓴다.
- `PRAGMA foreign_keys` 같은 SQLite 특유의 함정이 없다. InnoDB 는 FK 를 기본으로
  강제한다.

**MySQL 에서 반드시 다른 것 (SQLite 감각으로 쓰면 틀린다)**
- **컬럼 뒤에 붙인 `REFERENCES` 를 MySQL 은 무시한다.** 문법 에러도 나지 않고 FK 가
  그냥 안 만들어진다. 테이블 수준에 `FOREIGN KEY (...) REFERENCES ...` 로 써야 한다.
- `TEXT` 컬럼에는 길이 없이 인덱스(UNIQUE 포함)를 걸 수 없다 → `VARCHAR(n)`.
- `CREATE INDEX IF NOT EXISTS` 문법이 없다. FK 컬럼은 InnoDB 가 인덱스를 자동
  생성하므로 대개 불필요하다.
- `INSERT OR IGNORE` → `INSERT IGNORE`.

**Lombok** — 엔티티의 getter 와 기본 생성자를 줄인다. 단 **엔티티에는 `@Getter` 와
`@NoArgsConstructor(access = PROTECTED)` 까지만** 쓴다.
`@Data` · `@ToString` · `@EqualsAndHashCode` 는 JPA 엔티티에서 사고를 낸다 —
`toString()` 이 LAZY 연관을 건드려 세션 밖에서 예외를 내거나 양방향 연관에서 무한
재귀에 빠지고, `hashCode` 는 id 가 null 인 저장 전 시점에 동작이 이상해진다.

**남은 일** — `application.yml` 의 datasource 와 `build.gradle` 의 MySQL 드라이버는
사용자가 직접 연결한다. 그때까지 앱은 기동되지 않는다.

한 소스 트리에서 구분하려던 임시 구획이었다. 옛 백엔드는
[D-014](#d-014--옛-백엔드를-전환-없이-통째로-지운다) 에 따라 `3ee8788` 에서 통째로
지워졌다. **구분할 대상이 없으므로 구획도 필요 없다.**

**기각한 대안 — `_repo` 로 통일한다.** CLAUDE.md 에 적힌 규칙과는 맞지만, 완성 후
`_repo` 를 한 단계 위로 올리는 수순이 마지막에 한 번 더 필요하다. 그 수순에서
패키지 선언과 import 를 전부 다시 건드리게 된다.

**함께 고친 것** — `CLAUDE.md` 의 경로 규칙.

### D-030 · destination 1차는 조회 2개, 제안·승인은 인증 이후

**2026-09-22 · 확정** · 설계 문서:
[2026-09-22-destination-query-api-design.md](superpowers/specs/2026-09-22-destination-query-api-design.md)

`destination` 1차 범위는 **`GET /api/destinations`** 와 **`GET /api/destinations/{id}`**
두 개다.

**검토했으나 미룬 것 — 사용자 제안 → 관리자 승인.** 일반 사용자가 새 여행지 등록이나
기존 여행지 수정을 폼으로 요청하면 관리자가 확인 후 반영하는 흐름을 원했다. 이
기능은 *"누가 제안했는가"* 와 *"누가 관리자인가"* 를 알아야 성립하는데, 관리자는
[D-009](#d-009--1차-범위에서-관리자수집기감사로그모니터링을-뺀다) 에서 1차 범위 밖으로,
인증·세션·권한은 [D-019](#d-019--config-클래스와-security-의존성을-지운다) 에서 Task 2
로 미뤄 **둘 다 아직 없다.** 지금 만들면 제안자 컬럼을 담을 곳이 없어 스키마를 두 번
고치게 된다.

**언제 할 것인가 (2026-09-22 추가)** — 인증만 되면 바로가 아니라, **옛 기능을 전부
그린필드로 옮긴 뒤**에 한다. 사용자 결정. 제안·승인은 이 프로젝트에서 유일하게
*새로* 만드는 기능이고, 나머지는 이미 있던 것을 옮기는 일이다. 새 기능을 먼저
끼워 넣으면 아직 옮기지 않은 도메인과의 접점을 추측으로 설계하게 된다.

**정한 것들**
- 현 필터는 **이름**으로 받는다 (`?prefecture=교토부`). 현 47개는 이름이 바뀌지 않아
  자연키로 안전하고, 소비자가 현 목록 API 를 먼저 받을 필요가 없다.
  [D-025](#d-025--참조-테이블의-키를-id-로-둠다) 의 "키는 id" 는 **DB 내부** 규칙이고,
  API 표면은 별개로 본다.
- **없는 현 이름만 404.** 실재하는 현인데 여행지가 0건이면 `200 []` 다. 오타와 빈
  결과를 구분한다. 이를 위해 `PrefectureRepository.existsByName` 을 추가했다.
- 응답 DTO 는 **목록·상세 공용 record 하나.** 지도 때문에 목록에도 좌표가 필요해,
  나눠도 차이가 `description` 하나뿐이다.
- 변환은 **DTO 안의 정적 팩토리** `from(Destination)`. 별도 Mapper 를 만들지 않는다.
- Service 가 엔티티가 아니라 **DTO 를 반환한다.** `open-in-view: false` 이므로
  컨트롤러에서 LAZY 인 `prefecture` 를 건드리면 `LazyInitializationException` 이 난다.

**뺀 것** — 테스트 코드. 사용자 요청. 조회 2개뿐이라 `curl` 스모크로 확인한다.

### D-031 · 외부 API 캐시를 1차에서 뺀다

**2026-09-22 · 확정** · [D-009](#d-009--1차-범위에서-관리자수집기감사로그모니터링을-뺀다) 의 연장

날씨·환율 프록시에 **캐시를 넣지 않는다.** 매 요청마다 외부로 호출한다.
**예정된 리팩토링을 전부 마친 뒤 다시 검토한다.**

**이유** — 옛 설계의 Caffeine 캐시 5종 중 3종(`wikiSummary` · `wikiCategoryMembers` ·
`nominatimSearch`)은 **Wikipedia 수집기 전용**이고, 수집기는 D-009 로 범위 밖이다.
캐시가 정말 필요했던 이유는 **Nominatim 의 초당 1요청 제한**이었는데 그것이 사라졌다.

남은 둘의 사정은 다르다 — Open-Meteo 무료 한도는 하루 1만 건, Frankfurter 는 제한이
없다. 캡스톤 시연 규모로는 닿지 않는다. 프로젝트 `CLAUDE.md` 의 "성능 최적화는 명시
요청 없으면 넣지 않는다" 와도 맞는다.

**옛 설정을 그대로 가져오지 않는 이유** — `expireAfterWrite=7d` 가 5종 전체에 일괄
적용돼 있었다. 위키 문서에는 타당하지만 **날씨를 7일 캐시하면 지난주 날씨를 보여준다.**
수집기용 TTL 이 날씨에 잘못 상속된 것으로 보인다. 나중에 캐시를 넣더라도 이 값을
쓰지 않는다 — 날씨 30분, 환율 1시간 정도가 출발점이다.

**기각한 대안 — 캐시 없이 구조만 잡아둔다.** `@Cacheable` 만 빼고 Service 를 캐시
붙이기 좋게 만들어 두는 안. 실제로는 Service 메서드에 어노테이션 한 줄 다는 것이
전부라 미리 준비할 것이 없다. "나중을 위한 구조" 는 그 나중이 오지 않으면 그냥
빈 껍데기로 남는다.

**언제 다시 볼 것인가** — 옛 기능을 전부 그린필드로 옮긴 뒤. `TODO.txt` 에 적어둔다.

### D-032 · 외부 API 프록시(날씨·환율)를 1차에서 뺀다

**2026-09-22 · 확정** · [D-031](#d-031--외부-api-캐시를-1차에서-뺀다) 을 대체한다

`GET /api/weather` 와 `GET /api/fx` 를 **만들지 않는다.** `WebClient` 기반 외부 API
클라이언트도 만들지 않는다. 진행 순서에서 이 단계를 통째로 건너뛴다.

**D-031 이 성립하지 않게 된 이유** — D-031 은 "프록시는 만들되 캐시는 빼자" 였다.
프록시 자체를 빼기로 하면서 그 결정이 적용될 대상이 사라졌다. 판단이 틀렸던 것이
아니라 전제가 없어졌다.

**환율을 뺀 이유** — 사용자 판단. 환율은 **읽고 끝**이라 앱의 다른 기능과 엮이는
데가 없다. 즐겨찾기·코스·리뷰 어디에도 연결되지 않고 화면에 숫자 하나를 띄우는
것이 전부다.

**날씨도 같이 뺀 이유** — 같은 기준을 일관되게 적용했다. 날씨가 환율보다 나아 보였던
것은 여행지의 `lat/lng` 와 연결될 **가능성** 때문이었는데, 확인해 보니 옛 프론트에서
날씨도 환율과 나란히 `Header.jsx` 에 붙은 **표시 전용 위젯**이었다:

```
Header.jsx:86   <WeatherWidget />
Header.jsx:87   <FxWidget />
```

즉 현재 구조에서 둘의 역할은 같다. 날씨를 "헤더 위젯" 인 채로 옮기면 환율을 뺀
이유가 그대로 적용된다. 여행지 상세에 붙여 쓸모를 만들려면 그것대로 설계가 필요하고,
그 설계는 여행지·축제 쪽이 자리를 잡은 뒤에 하는 편이 낫다.

**얻는 것** — 새 의존성(`WebClient` 기반 클라이언트 4종)과 외부 서비스 장애라는
변수를 1차에서 제거한다. 남의 서버가 죽으면 우리 엔드포인트도 죽는데, 재시도·폴백은
프로젝트 `CLAUDE.md` 에서 "명시 요청 없으면 넣지 않는다" 로 막아둔 영역이다.
외부 연동을 미루면 그 문제를 아예 만나지 않는다.

**대가** — 옛 프론트의 `WeatherWidget.jsx` · `FxWidget.jsx` 가 호출할 곳이 없어진다.
프론트를 백엔드에 맞추는 단계에서 두 위젯을 걷어내거나 비활성화해야 한다
([D-008](#d-008--프론트를-백엔드에-맞춘다-전제-3개-해제)).

**언제 다시 볼 것인가** — 옛 기능을 전부 그린필드로 옮긴 뒤. 그때 날씨를 **여행지
상세에 붙이는 형태**로 설계한다. 캐시는 그다음 문제다 (D-031 의 TTL 메모는 유효하다 —
옛 7일을 그대로 쓰지 않는다).

### D-033 · 인증은 JWT + Spring Security 로 한다

**2026-09-28 · 확정** · 설계 문서:
[2026-09-28-user-auth-design.md](superpowers/specs/2026-09-28-user-auth-design.md)

옛 백엔드의 **세션 쿠키 방식을 버리고 JWT 로 간다.** Spring Security 필터 체인에
jjwt 0.12 로 만든 검증 필터를 붙인다. 토큰은 `Authorization: Bearer` 헤더로 주고받고,
Access 토큰 하나(24시간)만 쓴다.

**이유** — 사용자 판단. JWT 를 따로 공부하고 있고, 프로젝트에서 직접 설계하고
설명할 수 있기를 원했다. 세션이 기술적으로 부족해서 바꾸는 것은 아니다.

**대가**
- 옛 프론트는 세션 쿠키를 전제로 짜여 있다 (`credentials: 'include'`, `AuthContext`).
  Task 7 에서 토큰 저장과 헤더 부착을 추가해야 한다 ([D-008](#d-008--프론트를-백엔드에-맞춘다-전제-3개-해제)
  에 따라 프론트가 맞춘다).
- 서버가 토큰을 무효화할 수 없다. 로그아웃은 프론트가 토큰을 버리는 것이고, 탈취된
  토큰은 만료까지 유효하다. 블랙리스트는 넣지 않는다 (프로젝트 `CLAUDE.md`).

**기각한 대안**
- **세션 쿠키** — 프론트를 고치지 않아도 되고 로그아웃이 확실하다. 단일 서버인
  캡스톤 규모에는 오히려 더 맞는다. 위 이유로 채택하지 않았다.
- **HttpOnly 쿠키에 JWT 담기** — 프론트 변경은 적지만, 쿠키에서 토큰을 꺼내는
  필터를 따로 써야 하고 결국 세션과 같은 모양이 된다. JWT 를 쓰는 의미가 흐려진다.
- **Access + Refresh** — 저장 테이블 · 재발급 API · 프론트 재시도 로직이 붙는다.
- **`oauth2-resource-server`** — Spring 공식이고 코드가 짧지만, 검증 과정이 가려져
  발표에서 설명하기 어렵다.
- **Spring Security 없이 `HttpSession`/필터를 직접 작성** — "로그인 필요" 판정이
  엔드포인트마다 흩어진다. 이후 도메인 5개가 모두 인증을 쓰므로 한 곳에서 규칙으로
  관리하는 편이 낫다.

### D-034 · 에러 응답을 ErrorCode enum 하나로 통일한다

**2026-09-28 · 확정** · 코드별 설명: [ERRORS.md](ERRORS.md)

모든 에러 응답의 본문을 `ErrorResponse(code, message)` 하나로 쓴다. 발생할 수 있는 에러는
`common/error/ErrorCode` enum 에 `(HttpStatus, 고정 메시지)` 로 미리 정의하고, 서비스는
`throw new ApiException(ErrorCode.XXX)` 하나로 던진다. `ApiExceptionHandler` 는 이것과
Spring MVC 예외 5종(400·404·405·415)을 받고, 나머지는 catch-all 에서 500 으로 바꾼다.
필터 단계 401 은 `SecurityConfig` 의 EntryPoint 가 같은 `ErrorResponse` 로 쓴다.

**이유** — 3단계(favorite/review/history)부터 도메인이 늘어나기 전에 에러 모양을 한 번에
굳힌다. 지금은 `{"message"}` · `{"code","message"}` · Spring 기본 `{timestamp,status,...}`
세 가지가 섞여 나가서, 프론트가 에러를 한 가지 방식으로 다룰 수 없다. `code` 가 있으면
프론트는 문구가 아니라 코드로 분기하고, enum 하나가 "이 API 가 낼 수 있는 에러 목록" 이 된다.

**함께 정한 규칙**
- **메시지는 enum 의 고정 문구만.** 던지는 쪽에서 덮어쓰지 않는다. 그래서 문제가 된 값
  (`: 42`, `: 도쿄도`, `: 13`) 이 응답에서 빠진다. 클라이언트는 자기가 보낸 요청을 안다.
- **코드는 던지는 곳을 만들 때 추가한다.** 쓰는 곳 없는 코드는 미리 넣지 않는다.
  그래서 `FORBIDDEN`(course 소유권)과 `MISSING_PARAMETER`(필수 `@RequestParam`)는 아직 없다.
- **`IllegalArgumentException` → 400 일괄 매핑을 없앤다.** 의도한 400 은 전부 `ErrorCode` 로
  던진다. 일괄 매핑은 라이브러리가 던진 IAE(예: BCrypt 의 `rawPassword cannot be null`)까지
  "클라이언트 잘못" 으로 가려서, 서버 버그를 400 뒤에 숨긴다. 이제 그런 경우는 500 이다.
- **500 catch-all 에서만 `log.error` 를 남긴다.** 프로젝트 `CLAUDE.md` 의 "로깅 넣지 않음" 에
  대한 **명시적 예외**(사용자 승인). 응답에 원인을 싣지 않으므로 로그마저 없으면 500 의
  원인을 찾을 방법이 없다. 다른 곳에는 로그를 넣지 않는다.
- **Security 가 경로 판정보다 먼저다.** 비공개 경로의 없는 URL · 틀린 메서드는 로그인 전이면
  404 · 405 가 아니라 401 이다. 그대로 둔다.

**대가**
- 옛 핸들러가 주던 상세 메시지(`"id 값이 올바르지 않습니다: abc"` 등)가 사라진다.
- 목록에 없는 Spring 예외(406 등)는 500 으로 나간다. 현재 발생 경로는 없다.
- 필터 단계에서 난 인증 외 예외는 여전히 Spring 기본 본문이다 (`/error`). 그런 필터가 없다.
- 고정 문구가 `ErrorCode` 와 `scripts/smoke/error.sh` 두 곳에 있다. 문구가 계약이므로 일부러
  스모크가 검사하게 했다.

**기각한 대안**
- **상태별 예외 하위 클래스 유지** (`NotFoundException` 등 5개 + `ErrorCode`) — 상태가 예외
  클래스와 `ErrorCode` 두 곳에 중복되고, `new NotFoundException(LOGIN_FAILED)` 처럼 어긋나게
  써도 컴파일된다. 하위 클래스 5개를 지우고 `ApiException` 하나로 합쳤다.
- **`BusinessException(ErrorCode)` + 도메인별 하위 클래스** (`DestinationNotFoundException` 등) —
  흔한 방식이고 상태는 `ErrorCode` 한 곳이라 위 문제는 없다. 하위 클래스가 값을 하는 건 그 예외만
  `catch` 해 복구하거나 · 추가 데이터를 싣거나 · 핸들러에서 따로 다룰 때인데 지금은 셋 다 없어서
  빈 클래스만 코드 수만큼 는다. 기각이 아니라 보류: 그런 필요가 생긴 예외 하나만
  `extends ApiException` 으로 추가하면 되고, 핸들러는 부모 타입을 잡으므로 기존 코드는 안 바뀐다.
- **메시지 덮어쓰기 허용** (`new ApiException(code, "...: 42")`) — 어떤 값이 문제였는지 보이지만,
  문구가 던지는 곳마다 달라져 enum 이 목록 역할을 못 한다. 사용자 판단으로 고정 문구만 쓴다.
- **도메인별 enum** (`ErrorCode` interface + `DestinationErrorCode` 등) — 도메인 경계는 깔끔하지만
  전체 목록을 보려면 여러 파일을 열어야 한다. `common` 에 enum 하나, 주석 구역으로 나눈다.
- **`ResponseEntityExceptionHandler` 상속** — Spring 예외 ~15종을 한 번에 받지만 기본이
  ProblemDetail 이라 `handleExceptionInternal` 을 덮어쓰고 상태→`ErrorCode` 표를 따로 둬야 한다.
  실제로 쓰는 것은 5종이라 핸들러를 하나씩 두는 편이 읽기 쉽다.
- **enum 에 코드별 주석** — 처음에는 enum 항목마다 "어디서 · 무엇 때문에" 를 달았으나, 사용자
  판단으로 지우고 [ERRORS.md](ERRORS.md) 로 옮겼다. enum 은 목록만 보이게 짧게 둔다.
- **`@Valid` 입력 검증 · `AccessDeniedHandler`** — 프로젝트 `CLAUDE.md` 방침과 1차에 권한 분기가
  없다는 이유로 넣지 않았다.
