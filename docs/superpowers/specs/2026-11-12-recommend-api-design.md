## 1. 지금 상태 (정찰, 2026-11-12)

개인화에 쓸 수 있는 회원별 데이터가 네 종류 이미 있다.

| 테이블 | 내용 | 시연 시드의 `demo` 계정 |
|---|---|---|
| `favorite_destinations` | 찜한 여행지 | 10건 |
| `history_destinations` | 최근 본 장소 (`visited_at`) | 10건 |
| `review_destinations` | 평점 1 ~ 5 · 본문 | 2건 |
| `courses` · `course_stops` | 내 코스 | 2개 |

추천 대상은 여행지 219곳이다. `destinations` 에 있는 건 `name` · `prefecture_id` · `description`(위키 본문) · `lat` · `lng` 뿐이고 **테마 태그 컬럼이 없다**(S7 백로그). 그래서 성향을 읽을 재료는 설명 텍스트뿐이다 — 이게 이 기능에서 LLM 을 쓰는 이유다. 태그 없이 설명 문장으로 "사찰 위주" · "자연 위주"를 읽는 일은 SQL 로 못 한다.

TOP 25 의 종합 점수(D-076)는 `/api/destinations/ranking` 에 이미 있고, 규칙 추천과 폴백에서 재사용한다.

**날씨 API 는 지금 쓰지 않는다.** 백엔드에 호출 코드가 없고, `components/WeatherWidget.jsx` · `components/FxWidget.jsx` 는 어디서도 import 되지 않는 죽은 파일이며, `application.yml` 의 `external.open-meteo` · `external.frankfurter` 는 설정만 남은 껍데기다(D-032 로 기능을 뺐다).

## 2. 정한 것

- 모델은 OpenAI `gpt-5-mini`. 모델 id 는 `application.yml` 설정으로 빼서 코드에 박지 않는다.
- 키는 백엔드 환경변수 `OPENAI_API_KEY` 하나. **프론트에서 OpenAI 를 직접 부르지 않는다** — 공개 URL 이라 키가 브라우저에 노출되면 남이 내 요금으로 쓴다.
- **스키마를 바꾸지 않는다.** 추천 결과를 저장하지 않고 화면 상태로만 둔다. 배포가 단순해지고 되돌릴 것이 없다.
- 새 도메인 패키지 `com.japantravel.recommend.{controller,service,dto}` — `entity` · `repository` 는 없다. 서비스가 `favorite` · `history` · `review` · `destination` 의 리포지터리를 읽는다.
- 호출은 사용자가 버튼을 누를 때만. 화면이 열릴 때 자동으로 부르지 않는다.
- 추천은 **여행지만** 한다. 축제는 넣지 않는다(기간 판정이 붙어 조각이 커진다).

## 3. 계약

`/api/me/...` 는 로그인 사용자별 리소스에 쓰는 기존 규칙이다(`/api/me/favorites` · `/api/me/history`).

| 메서드 | 경로 | 권한 | 상태 | 응답 `data` |
|---|---|---|---|---|
| GET | `/api/me/recommendations?limit=5` | 🔑 | 200 | `RecommendationResponse` |

- `limit` 기본 5, 최대 10.
- 토큰 없음 → 401 `UNAUTHORIZED` (기존 규칙). **새 에러 코드는 만들지 않는다.**
- 찜 · 기록 · 리뷰가 모두 0건인 계정도 에러가 아니다 — `source: "RULE"` 로 인기 상위를 돌려준다.

```
RecommendationResponse = {
  source: "AI" | "RULE",
  items: RecommendationItem[],
  basis: { favoriteCount, historyCount, reviewCount, topPrefectures: string[] }
}
RecommendationItem = { reason: string, destination: DestinationResponse }
```

`reason` 은 40자 안의 한 문장. `destination` 은 기존 `DestinationResponse` 를 그대로 쓴다 — TOP 25 의 `DestinationRankingResponse` 가 `destination` 을 품는 것과 같은 모양이다. `basis` 는 화면에 "찜 10 · 최근 본 10 을 반영했습니다"로 보여 추천이 어디서 나왔는지 드러낸다.

## 4. 후보 선정 (규칙)

LLM 에게 219곳을 다 주지 않는다. SQL 로 40곳까지 좁힌 뒤 그 목록에서만 고르게 한다.

1. **제외** — 이미 찜한 곳, 최근 본 곳, 리뷰를 쓴 곳.
2. **채움 ①** — 찜 · 최근 본 곳의 현(prefecture) 상위 3개에 속한 여행지를 현당 최대 8곳.
3. **채움 ②** — 종합 점수(D-076) 상위에서 40곳이 될 때까지.
4. 40곳이 안 되면 그대로 보낸다.

이 단계가 "검색"에 해당한다. 벡터 유사도 대신 이력 기반 SQL 을 쓴다.

## 5. 프롬프트와 응답 검증

- 후보는 `{id, 이름, 현, 설명}` 으로 넣는다. **설명은 자르지 않는다** — 실측 길이가 중앙 37자 · 최대 57자다(2026-11-12 측정, 219곳 전부의 이름+현+설명 합계 10,572자). 사용자 이력은 `{이름, 현}` 목록과 리뷰 평점.
- 응답은 JSON 스키마로 고정한다 — `{"items":[{"id":number,"reason":string}]}`.
- **검증** — 돌아온 `id` 가 후보 목록에 없으면 버린다. 이것으로 없는 장소가 화면에 올라오는 일이 막힌다. 유효한 것이 `limit` 보다 적으면 규칙 상위로 채운다. `reason` 이 60자를 넘으면 자른다.
- 토큰은 입력 약 6,000 · 출력 약 400.

## 6. 폴백

아래 중 하나라도 걸리면 `source: "RULE"` 로 규칙 추천을 돌려준다. **재시도는 하지 않는다**(CLAUDE.md).

| 언제 | 처리 |
|---|---|
| `OPENAI_API_KEY` 없음 | 바로 규칙 추천. 채점자가 키 없이 재현할 수 있어야 한다 |
| 10초 타임아웃 · HTTP 오류 | 규칙 추천 |
| JSON 파싱 실패 · 유효 id 0개 | 규칙 추천 |
| 찜 · 기록 · 리뷰 0건 | 규칙 추천 + "찜을 하면 맞춤 추천이 됩니다" |

규칙 추천의 `reason` 은 템플릿으로 쓴다 — "찜한 교토부의 인기 여행지", "많이 찾는 곳". 화면에는 `source` 를 배지로 보여 AI 가 고른 것과 기본 추천을 구분한다.

## 7. 화면

| 경로 | 권한 | 내용 |
|---|---|---|
| `/recommend` | 공개(내용은 로그인에 따라 다름) | "○○님을 위한 추천" + [추천 받기] 버튼 + 카드 5개(사진 · 이름 · 현 · 이유) + `basis` 한 줄 |

- 상단 메뉴에 "추천"을 더한다 — 여행지 · 축제 · 여행코스 · TOP 25 · 뉴스 · 추천 (6개). 모바일 메뉴도 같은 목록을 쓴다(B-6 과 같은 방식).
- 카드를 누르면 기존 `/detail/destination/:id` 로 간다.
- 버튼을 누른 동안에는 "고르고 있어요" 상태를 보여 준다(3 ~ 5초).

## 9. 하지 않을 것

벡터DB · 임베딩(아래 기각), 추천 결과 저장, 재시도, 추천 품질 오프라인 평가, 축제 추천, 추천 이유의 다국어.

## 10. 기각한 대안

- **RAG (벡터DB + 임베딩 검색)** — 여행지가 219곳이라 후보를 좁히면 **설명까지 전부 프롬프트에 들어간다.** 검색해서 찾아와야 할 만큼 많은 데이터가 아니다. 벡터 저장소 의존성, 청킹, 임베딩 비용, 데이터가 바뀔 때 인덱스 재생성이 늘고 전시 1주 전에 설정할 것만 늘어난다. 또 대상이 유명 관광지라 모델이 이미 아는 내용이어서 검색으로 보강할 것도 적다. 보고서에는 "검토했고 데이터 규모 때문에 기각"으로 적는다 — 이 판단 자체가 발표 재료다.
- **219곳 전체를 프롬프트에** — ~~호출당 입력 2만 토큰, 응답 10초 이상~~ **추정 정정(2026-11-12)**: 실측하니 219곳 전부가 약 1만 토큰, 호출당 3 ~ 4원으로 후보 40곳과 거의 같다. 비용 · 속도는 기각 이유가 되지 못한다. 그래도 후보를 좁히는 쪽을 쓰는 이유는 ① 이미 찜 · 본 곳 제외는 어차피 SQL 로 해야 하고 ② 40곳이면 출력이 안정적이며 ③ 5곳을 고르는 데 219곳을 다 보일 필요가 없기 때문이다. 셋 다 결정적이지는 않아서 **승인 때 다시 묻는다**(§12-4).
- **순서는 규칙 · LLM 은 이유 문장만** — 가장 안전하지만 사람마다 비슷한 목록이 나와 "회원별"이라는 말이 약해진다.
- **로컬 LLM (Ollama)** — AWS 배포본(t3.small)에서 돌지 않아 배포와 AI 기능이 반으로 쪼개진다. 노트북 사양에 달리고 모델 다운로드와 사양 스파이크로 반나절이 더 든다. 비용은 호출당 0원이지만 남은 7일이 더 비싸다.
- **추천 결과 테이블 추가** — 전시 1주 전 스키마 변경. 캐시 이득보다 배포가 단순한 쪽이 낫다.
- **홈 상단 섹션 / 마이페이지 새 탭** — 사용자가 전용 페이지 + 상단 메뉴를 골랐다.
